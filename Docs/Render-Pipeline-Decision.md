# 렌더 파이프라인 결정: PC 게임이지만 HDRP 대신 URP

| 항목 | 내용 |
| --- | --- |
| 결정일 | 2026-11-02 |
| 상태 | 확정 |
| 결정 | **Unity 6 + URP(PC 사양) + 직접 만드는 렌더러 기능** |
| 대상 | PC (기준 사양: GTX 1060급, 1080p 출력, 60fps) |
| 검토한 대안 | HDRP, Unreal Engine |

## 요약

> PC 게임이라 HDRP를 쓸 수 있었지만, 이 프로젝트 그래픽의 뼈대는 **광원마다 직접 계산하는 툰 조명과 픽셀 버퍼 위의 선화**다.
> HDRP는 조명을 엔진 내부 구조에서 한꺼번에 합치기 때문에 이 제어가 어렵고, 엔진을 업데이트할 때마다 다시 손봐야 할 위험이 크다.
> HDRP가 확실히 앞서는 기능은 볼류메트릭(빛줄기·안개) 하나이며, 이는 URP에서 저해상도 버퍼 레이마칭으로 직접 만들 수 있다.
> 목표 레퍼런스인 Replaced도 Unity에서 기성 파이프라인 대신 렌더링 파이프라인을 직접 만들었다.

## 배경

- 목표 스타일: **Replaced의 디테일하고 조명이 풍부한 배경 + Never's End의 도트 캐릭터.**
- 렌더링 방식: 3D 장면을 약 640×360 픽셀 버퍼에 그리고 정수 배율로 확대한다. 카메라는 텍셀 격자에 스냅하고, 남은 소수점 위치는 업스케일 단계에서 반영한다.
- 직접 만든 핵심 기능:
  - `Sprite Toon` 셰이더: 광원별 툰 단계, 그림자 색, Built-in 방식 횃불 감쇠, 물웅덩이·적설·바람·평면 반사
  - 물체 ID 기반 1픽셀 선화 (RenderGraph 렌더러 기능)
  - 캐릭터 가림 해소: 나무 투명화, 벽 뒤 실루엣 (스텐실 패스)
- 처음에는 모바일 대상이라 URP를 선택했고(2026-11-02), 같은 날 PC 대상으로 바꾸면서 HDRP를 다시 검토했다.

## 검토 결과

### 1. HDRP

**HDRP가 주는 것**
- 볼류메트릭 안개·빛줄기, 물리 기반 노출, 하늘·구름, SSR, SSGI, 레이트레이싱, 고품질 피사계 심도
- 광원 수 제한이 사실상 없음

**HDRP를 쓰지 않은 이유**

1. **광원별 커스텀 툰 조명을 넣기 어렵다.**
   - HDRP 재질은 엔진 내부 함수(`EvaluateBSDF`)에서 조명을 계산하고, 조명 루프가 한 픽셀에 닿는 광원을 한꺼번에 합친다. 그래서 광원마다 다른 툰 램프를 적용하기 어렵다.
   - Unity의 Shader Graph 커스텀 조명 예제는 URP 전용이다. HDRP와 커스텀 조명 모델은 셰이더 코드로 직접 작성하라고 문서에 나와 있다.
   - Never's End 발표의 핵심인 "빛마다 툰 램프"가 바로 이 부분이다.
2. **나중에 수정하고 보완하기가 어렵다.**
   - 직접 작성한 셰이더를 HDRP 내부 재질 구조에 붙여야 한다. 이 구조는 버전마다 바뀌어 왔다(예: Lambert 처리 방식 변경으로 기존 커스텀 재질 수정 필요).
   - 지금 URP 셰이더는 공개 API(`GetMainLight`, `GetAdditionalLight`, `LIGHT_LOOP_BEGIN`)만 쓴다. 이 API는 여러 버전에 걸쳐 유지되어 왔다.
3. **이미 만든 기능을 다시 써야 한다.**
   - 선화, 가림 해소, 픽셀 버퍼 관련 렌더러 기능을 HDRP Custom Pass로 다시 작성해야 한다. 노출·TAA·볼류메트릭 버퍼도 픽셀 해상도에 맞춰 다시 조정해야 한다.
4. **풍부한 기능 상당수가 픽셀아트와 잘 맞지 않는다.**
   - TAA, 볼류메트릭 안개, SSGI, SSR은 이전 프레임을 재사용(시간 누적)한다. 360p 픽셀 버퍼에서는 잔상과 번짐이 생겨 또렷한 도트를 해친다. 결국 끄거나 크게 조정하게 되어 HDRP를 쓰는 이점이 줄어든다.
5. **더 무겁다** (비교할 수 없을 정도는 아님).
   - 셰이더 변형과 기본 리소스가 많아 빌드 크기와 셰이더 컴파일 시간이 늘어난다. 기본으로 깔리는 연산(조명 버퍼, 화면 공간 효과, 노출)도 많다.
   - 내부 버퍼가 작아서 PC에서 실행 비용은 감당할 수 있는 수준이다. 실제 용량 차이는 빌드하지 않아 측정하지 않았다.
6. **대안 패키지도 불확실하다.**
   - Unity 공식 Toon Shader 패키지는 HDRP 지원을 명시한다. 하지만 실험 단계이고, Unity 6에서 컴파일되지 않는다는 보고가 있으며, 지원 버전 범위가 명확하지 않다.
   - 그 패키지를 쓰더라도 물웅덩이·적설·바람·반사 기능을 다시 옮겨 넣어야 한다.

### 2. Unreal Engine

- 현재 구현(C# 스크립트, Sprite Toon 셰이더, URP 렌더러 기능, 검증·씬 생성 스크립트)을 전부 다시 만들어야 한다.
- Never's End 기법을 Unreal 5로 구현한 사례(참고 자료 1)에서 문제가 확인됐다.
  - 디퍼드 조명이 깊이 버퍼에서 위치를 복원하기 때문에, 스프라이트 정렬용 깊이 밀기와 충돌했다.
  - 그래서 엔진 조명을 끄고 후처리에서 그림자와 명암을 직접 계산해야 했다.
  - 같은 글에서 **Unity URP(포워드)는 실제 정점 위치로 조명하므로 이 문제가 없다**고 했다.
- 셰이딩 모델이 엔진에 고정되어 있어, 광원별 툰 램프를 넣으려면 엔진 소스를 수정하거나 후처리로 우회해야 한다.
- Lumen과 볼류메트릭 안개는 강력하지만, 픽셀 버퍼에서는 HDRP와 같은 시간 누적 잔상 문제가 생긴다.

### 3. URP (선택)

**URP를 선택한 이유**
- 툰 조명, 선화, 가림 해소, 픽셀 버퍼 같은 프로젝트 고유 기능이 **지금 그대로 동작한다**. 자동 검증 11종을 모두 통과했다.
- 렌더러 기능(RenderGraph)과 직접 작성한 셰이더로 **확장 지점이 열려 있다.** Replaced처럼 "직접 만드는 렌더링"에 가깝다.
- PC 사양으로 필요한 것을 확보할 수 있다.

  | 필요 | URP에서의 방법 |
  | --- | --- |
  | 많은 생활 조명 (Replaced: 최대 60개) | Forward+ (물체당 광원 한도 해제) |
  | 빛 번짐 | HDR + 픽셀 버퍼 Bloom |
  | 색 보정·비네트·피사계 심도·SSAO | URP 기본 후처리 |
  | 빛줄기·안개 | **직접 구현**: 픽셀 해상도 레이마칭 + 높이 안개 |

**URP를 선택하며 감수하는 것**
- 볼류메트릭 빛줄기와 높이 안개를 직접 만들고 유지해야 한다.
- 하늘·구름 시스템, SSR, 레이트레이싱은 없다. 이 스타일에서는 필요성이 낮다고 판단했다.

## 왜 렌더링 기능을 직접 만드는가

### 범위: 렌더러 전체가 아니라, 기성 렌더러에 없는 부분만

| 방식 | 내용 | 이 프로젝트 |
| --- | --- | --- |
| 기성 렌더러 그대로 | URP/HDRP 기본 셰이더와 후처리만 사용 | X |
| **기성 렌더러 + 직접 만드는 기능** | URP가 화면 그리기·그림자·광원 관리·후처리를 맡고, 스타일 고유 부분만 렌더러 기능과 셰이더로 직접 작성 | **O** |
| 렌더러를 처음부터 작성 | Scriptable Render Pipeline을 직접 구현 (Replaced의 방식으로 알려짐) | X |

렌더러를 처음부터 작성하면 그림자, 광원 컬링, 후처리, 플랫폼 대응까지 모두 직접 유지해야 한다.
1인·소규모 개발에서는 비용이 크다. URP가 이미 잘 하는 부분은 URP에 맡긴다.

### 기성 렌더러에 없는데 이 스타일에 꼭 필요한 것

"3D로 그린 픽셀아트"는 일반 3D 렌더링과 목표가 다르다.
일반 3D 렌더러는 **더 부드럽고 사실적으로** 만드는 데 맞춰져 있다(안티앨리어싱, 시간 누적, 물리 기반 조명).
이 스타일은 **매 프레임 같은 픽셀이 같은 자리에 또렷하게** 찍히는 것이 목표다.

| 필요한 것 | 기성 렌더러에 없는 이유 | 직접 만든 기능 |
| --- | --- | --- |
| 저해상도 픽셀 버퍼 + 정수 배율 확대 + 서브픽셀 보정 | 렌더 스케일은 있지만 텍셀 격자 스냅과 스크롤 보정이 없음 | `ExplorationCamera` |
| 카메라·캐릭터 텍셀 격자 스냅 | 일반 카메라는 연속 이동이 정상 | `ExplorationCamera`, `PixelCharacterAlignment` |
| 광원별 툰 램프, 그림자 색, 횃불 감쇠 | 기본 조명은 물리 기반 연속 명암 | `Sprite Toon` 셰이더 |
| 물체 단위 1픽셀 선화 (물체 경계 > 깊이 > 법선 우선순위) | 기본 외곽선 기능이 없음 | 물체 ID 패스 + 선화 패스 (렌더러 기능) |
| 조정한 법선 (넓은 명암 덩어리) | 메시 법선을 그대로 사용 | `AuthoredNormalProfile` |
| 계단식 애니메이션 | 애니메이터는 매 프레임 보간 | `ExplorerMotor.animationFrameRate` |
| 캐릭터 가림 해소 (나무 디더, 벽 뒤 실루엣) | 게임 고유 연출 | 스텐실·스캔 패스 (렌더러 기능) |
| 픽셀 단위 빛줄기·높이 안개 | URP에 볼류메트릭 없음. HDRP 것은 시간 누적이라 픽셀 버퍼에서 잔상 | 계획: 픽셀 해상도 레이마칭 (배경 조명 설계 L4·L5) |

### 이 방식의 장점

- **스타일을 끝까지 제어한다.** 명암 단계, 선화 굵기, 빛줄기 단계 수처럼 그림체를 정하는 값이 모두 우리 코드에 있다.
- **업데이트에 덜 흔들린다.** URP의 공개 API(광원 함수, 렌더러 기능, RenderGraph)에만 기대고 엔진 내부 구조는 건드리지 않는다.
- **필요한 만큼만 비용을 쓴다.** 범용 사실적 효과를 끄고 다시 맞추는 대신, 픽셀 버퍼 해상도에서 필요한 효과만 계산한다.
- **검증할 수 있다.** 기능마다 자동 검증 스크립트가 픽셀 단위로 결과를 확인한다.

### 이 방식의 비용

- 직접 만든 기능은 직접 유지보수한다(셰이더, 렌더러 기능, 검증 스크립트).
- URP 메이저 버전을 올릴 때 렌더러 기능의 RenderGraph 코드를 점검해야 한다.
- 볼류메트릭처럼 기성 렌더러에 있는 기능도 스타일에 맞추려면 새로 만들어야 한다.

### 파이프라인 전체를 직접 만들 때만 확실히 얻는 것

| 기술 | 내용 |
| --- | --- |
| 배경 캐싱, 부분 다시 그리기 | 카메라가 텍셀 단위로만 움직이므로 정지한 배경은 한 번 그려 두고, 움직이는 물체만 매 프레임 다시 그린다 |
| 층별 해상도·프레임레이트 합성 | 배경은 고밀도, 캐릭터는 저밀도 도트. 캐릭터 12fps, 배경 60fps처럼 층마다 따로 그려 합성한다 |
| 그림자·광원 관리 | 정적 광원 그림자를 캐싱하고 움직이는 물체만 갱신한다. 생활 조명 다수에 그림자를 줄 수 있다 |
| 불필요한 패스 제거 | 시점 전용으로 컬링과 패스를 최소화해 낮은 사양에서도 광원을 많이 쓴다 |

툰 조명, 선화, 볼류메트릭, 월드 고정 디더·팔레트, 물체 정렬은 URP + 직접 만드는 기능으로도 구현할 수 있다.
위 네 가지가 필요해질 만큼 성능이나 표현이 막히면 파이프라인 전체 제작을 검토한다(아래 재검토 조건).

## Replaced의 사례

- 엔진: Unity (참고 자료 2)
- 렌더링: 개발팀이 렌더링 파이프라인을 처음부터 직접 만들었다고 한다 (참고 자료 3).
- 2D는 캐릭터뿐이고, 나머지는 픽셀아트처럼 꾸민 3D다.
- 평면 캐릭터에 입체감을 주려고 작은 램프를 곳곳에 정밀하게 배치했다. GTX 1060에서 실시간 광원을 최대 60개까지 동시에 쓴다.
- 볼류메트릭과 후처리를 구체적으로 어떻게 구현했는지는 찾지 못했다.

## 다시 검토할 조건

다음 중 하나에 해당하면 이 결정을 다시 본다.
- 툰 조명을 포기하고 물리 기반 조명으로 스타일을 바꿀 때
- 직접 만든 볼류메트릭이 품질이나 성능 목표(픽셀 버퍼에서 1ms 이하)를 맞추지 못할 때
- HDRP가 커스텀 조명 모델을 공식 지원하게 될 때
- 대상 플랫폼이 다시 바뀔 때
- 생활 조명 그림자 수나 배경 렌더 비용이 URP 구조 안에서 목표 프레임을 맞추지 못할 때 (파이프라인 전체 제작 검토)
